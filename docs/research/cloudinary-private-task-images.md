# Cloudinary for private Task images

**Verified:** 2026-08-03  
**Scope:** Cloudinary Image & Video API as the provider for Pravah's confirmed Android-first workflow: up to five ordered static images per Task, direct background uploads, optimized variants, private delivery, recoverable removal, and provider cleanup.  
**Method:** Official Cloudinary pricing, product documentation, and API references only. No Cloudinary account was available in this repository, so account configuration and actual usage remain unverified.

## Decision

Cloudinary is a **conditionally suitable** foundation for Task images. Its upload, transformation, storage, deletion, monitoring, and Android-direct-upload capabilities fit the workflow. It should remain the selected provider for specification work, subject to two gates:

1. Pravah must choose the precise meaning of "private." Free-plan `authenticated` assets with signed delivery URLs prevent guessing and unsigned access, but a signed URL is a reusable bearer link and Cloudinary explicitly warns that signing does not prevent link sharing. Expiring token-based CDN access requires Advanced or higher. The free-plan time-limited private-download endpoint is not CDN-cached and is billed at twice the delivered bandwidth.
2. The real Cloudinary product environment must be provisioned and checked for its plan, region, limits, backup setting, strict-transformation setting, and signed-URL invalidation behavior before implementation is called ready.

The commonly stated allowance is also misstated: Cloudinary does **not** provide "$25 worth of credits." Its Free plan costs $0 and currently supplies **25 pooled monthly credits**. A credit is a usage unit, not a dollar balance.

## Current pricing and capacity

### Official facts

- The Free plan is $0, free forever, requires no credit card, and includes 25 monthly credits. Plus is listed at $99/month (or $89/month billed yearly) for 225 credits; Advanced is $249/month (or $224/month billed yearly) for 600 credits; Advanced Extra is $549/month (or $494/month billed yearly) for 1,350 credits; and Pro PAYG is $1,099/month (or $989/month billed yearly) for 2,750 included credits plus billed overage. ([pricing](https://cloudinary.com/pricing), [plan comparison](https://cloudinary.com/pricing/compare-plans), [billing and plans](https://cloudinary.com/documentation/billing_and_plans))
- One credit equals 1,000 transformations, **or** 1 GB of managed storage, **or** 1 GB of image bandwidth. Usage is additive across all three categories; 5 GB stored + 10 GB delivered + 5,000 new transformations consumes 20 credits. Free, Plus, Advanced, and Advanced Extra calculate transformation and bandwidth usage over a rolling 30-day window. ([billing and plans](https://cloudinary.com/documentation/billing_and_plans))
- Storage usage includes the stored master, cached derived assets, and any revisions held in Cloudinary backup storage. Bandwidth is the size of successfully delivered assets. An incoming transformation consumes a transformation credit; each newly generated eager derivative also consumes one, while repeat delivery of a cached derivative does not create another transformation charge. ([billing and plans](https://cloudinary.com/documentation/billing_and_plans))
- Free-plan image uploads are limited to 10 MB and 25 megapixels. The Free Admin API allowance is 500 requests/hour. Plus raises the file limit to 20 MB while retaining 25 MP, and its Admin API allowance is 2,000/hour. ([plan comparison](https://cloudinary.com/pricing/compare-plans))

### Inference for Pravah

- Optimizing a source before or during upload lowers persistent storage, future bandwidth, and the size of every downstream variant. Keeping a small fixed set of eager variants bounds both transformation creation and derived storage.
- The 25-credit Free plan could accommodate a modest single-user workload, but no defensible cost forecast exists without the number of retained images, normalized master size, variant sizes, and monthly views. The implementation should meter all three contributors rather than treating "25 credits" as 25 GB of storage.
- `f_auto` can create different derived formats for the same transformation and thereby increase transformation and storage usage. For a native Android-only client, a fixed, platform-decodable output format may be more predictable than browser-oriented `f_auto`; Cloudinary itself warns that native system frameworks do not universally decode WebP. ([image optimization](https://cloudinary.com/documentation/image_optimization))

## Upload security and Android flow

### Official facts

- Cloudinary supports direct client/mobile uploads. Signed upload requests include an API key, timestamp, and signature generated with the API secret. The signature covers the timestamp and other request parameters, is valid for one hour, and must be generated by a backend; Cloudinary says never to expose the API secret in client code. ([upload guide](https://cloudinary.com/documentation/upload_images), [Upload API](https://cloudinary.com/documentation/image_upload_api_reference))
- A signed upload preset supports all upload parameters. Request parameters normally override preset values, except eager and incoming transformations, which are merged. Unsigned presets are discoverable in client code and accept a restricted parameter set. ([upload presets](https://cloudinary.com/documentation/upload_presets))
- The Upload API accepts one file per request. Cloudinary recommends starting concurrent uploads modestly (about ten), reducing concurrency on HTTP 420, and retrying with exponential backoff. The Admin API has a documented hourly limit; the Upload API has no fixed Admin-style quota but can still return 420 at account limits. ([upload guide](https://cloudinary.com/documentation/upload_images), [Admin API](https://cloudinary.com/documentation/admin_api))
- Cloudinary's Android SDK accepts file paths, byte arrays, resources, or URIs and can queue uploads through Android background jobs, report asynchronous progress, retry recoverable network failures, apply network/charging policies, and cancel individual requests. It still requires Pravah's backend to provide the signature for signed uploads. ([Android uploads](https://cloudinary.com/documentation/android_image_and_video_upload))

### Inference for Pravah

- The Android app can upload bytes directly to Cloudinary without routing image bodies through Convex: an authenticated Pravah backend function should issue a short-lived, tightly parameterized signature only after authorizing the user and Task-image slot. The API secret stays server-side.
- Because signed-request parameters can override a signed preset, the backend should sign the exact allowed delivery type, asset identifier/folder, incoming normalization, eager variants, and other restrictions rather than issue a generic signature. App-side five-image limits are not a security boundary; the signature endpoint must enforce ownership and quota.
- A successful client upload should not become an owned Task image solely because the client reports a public ID. The backend design should validate the Cloudinary response/signature or reconcile the asset server-side before committing provider metadata.

## Private delivery is the deciding constraint

### Official facts

- A `private` asset protects the original, but derived transformations are public by default. Strict Transformations can prevent unsigned, unapproved transformation generation; this does not by itself make an already generated URL user-specific. ([media access control](https://cloudinary.com/documentation/control_access_to_media))
- An `authenticated` asset protects the original and every derived asset; each delivery requires an exact signed URL. Authenticated assets cannot use arbitrary on-the-fly transformations: required derivatives must be generated eagerly during upload/update and Cloudinary returns their signatures. ([media access control](https://cloudinary.com/documentation/control_access_to_media))
- Cloudinary describes ordinary signed delivery URLs as authorization against unauthorized or manipulated URLs but cautions that they do not prevent sharing: anyone who obtains the URL can access the asset. ([media access control](https://cloudinary.com/documentation/control_access_to_media))
- Token-based access can expire by time, IP, or path, but it is a premium feature requiring Advanced or higher and an encryption key provisioned by Cloudinary. Cookie-based access also needs a CNAME at additional cost. ([media access control](https://cloudinary.com/documentation/control_access_to_media))
- The `private_download_url` API produces an expiring signed URL (one hour by default), but each request bypasses CDN caching and Cloudinary warns not to embed it because delivery costs twice the bandwidth. ([media access control](https://cloudinary.com/documentation/control_access_to_media))

### Inference for Pravah

- If "private" means unguessable and inaccessible without first receiving a backend-authorized bearer URL, Free-plan authenticated delivery can meet that weaker definition. It cannot revoke an already leaked signed CDN URL on session logout or at a short expiry.
- If "private" means short-lived, user-session-bound delivery, the production choices are either Advanced token access (currently $249/month list price), an application-controlled proxy/CDN design outside the current assumption, or the uncached double-bandwidth private-download endpoint. That product/security choice belongs in **Define secure upload and delivery authorization**.
- Use `authenticated`, not merely `private`, if any display variant must remain protected. Pre-generate only the bounded Android variants that the product actually uses.

## Normalization, formats, and metadata

### Official facts

- Cloudinary stores uploads unchanged by default. An incoming transformation can limit dimensions before the resulting master is stored and can apply a concrete format/quality; `f_auto` must not be used as an incoming transformation because it is resolved at delivery time. ([eager and incoming transformations](https://cloudinary.com/documentation/eager_and_incoming_transformations))
- The transformation API provides `fl_force_strip` to clear IPTC, EXIF, and XMP during an incoming transformation. (`fl_strip_profile` is narrower: it converts to sRGB and strips the ICC profile.) Cloudinary's normal transformed delivery strips almost all metadata, but that delivery behavior does not alter the stored original. ([transformation reference](https://cloudinary.com/documentation/transformation_reference), [image optimization](https://cloudinary.com/documentation/image_optimization))
- `q_auto` selects content-aware compression. `f_auto` can deliver WebP, AVIF, JPEG XL, or a fallback based on the request, account, and enabled formats; different `f_auto` results may create additional derived assets. ([image optimization](https://cloudinary.com/documentation/image_optimization), [format support](https://cloudinary.com/documentation/image_format_support))

### Inference for Pravah

- The accepted rule that originals and GPS/EXIF are not retained requires normalization **before the stored master**—either reliably on-device or through an incoming transformation including metadata stripping. Relying on Cloudinary's default transformed-delivery stripping would leave metadata in the stored source.
- Exact dimensions, master/output formats, quality, transparency policy, and maximum normalized bytes remain a separate measured decision. The provider supports the necessary controls but does not decide the quality bar for Pravah.

## Deletion, recovery, and cache behavior

### Official facts

- The signed Upload API `destroy` method deletes one asset; Admin API delete methods handle multiple assets and are server-side only. A client-upload response can also contain a delete token valid for ten minutes. ([deletion guide](https://cloudinary.com/documentation/delete_assets))
- `destroy` can set `invalidate: true`. Cloudinary says invalidation normally propagates in seconds to minutes, but delivered copies can otherwise remain cached in its CDN for up to 30 days and can also persist in browsers or external proxies. ([Upload API](https://cloudinary.com/documentation/image_upload_api_reference), [CDN invalidation](https://cloudinary.com/documentation/invalidate_cached_media_assets_on_the_cdn))
- Signed URLs are not invalidated by default; Cloudinary says to submit a support request to enable signed-URL invalidation. Bulk Admin API invalidation is also not enabled by default. ([CDN invalidation](https://cloudinary.com/documentation/invalidate_cached_media_assets_on_the_cdn))
- Automatic backup is off by default and available on all plans. If enabled in Cloudinary storage, backups count toward managed storage. Deleting an active asset does not necessarily erase its backup; individual backed-up versions can be deleted through the Admin API, while clearing all default Cloudinary backup storage requires support. ([backups and version management](https://cloudinary.com/documentation/backups_and_version_management), [Admin API](https://cloudinary.com/documentation/admin_api))

### Inference for Pravah

- Pravah should keep recoverability in its own product lifecycle: delay Cloudinary deletion until the Task/image recovery window expires, then call server-side `destroy` with invalidation and retry idempotently. Do not give the mobile client deletion authority.
- Before release, verify signed-URL invalidation on the real product environment. Without it, permanent deletion may leave previously delivered signed copies available from Cloudinary's CDN until cache expiry.
- Decide whether Cloudinary automatic backup is disabled. If enabled, permanent product deletion requires a separate backed-up-version purge process and changes both privacy semantics and storage cost.

## Monitoring, limits, and operational constraints

### Official facts

- Current plan and actual transformation/storage/bandwidth consumption are visible in Console. The Admin API `GET /usage` reports usage and limits, and every Admin API response returns rate-limit headers. ([usage data](https://cloudinary.com/documentation/programmable_media_asset_usage_data), [Admin API](https://cloudinary.com/documentation/admin_api))
- At about 90% of a quota, Cloudinary displays Console warnings and emails account administrators or the billing address. Fixed-plan limits are soft initially, but after repeated notices an over-limit account can be disabled; uploads and new transformations are then blocked, and delivery can eventually be blocked. Custom percentage thresholds are documented only for Enterprise. ([usage data](https://cloudinary.com/documentation/programmable_media_asset_usage_data))
- Cloudinary uses US-based data centers by default. EU or Asia-Pacific data centers are an Enterprise-only premium feature that must be arranged when the account is created. ([Admin API](https://cloudinary.com/documentation/admin_api), [storage FAQ](https://cloudinary.com/documentation/developer_onboarding_faq_storage))

### Inference for Pravah

- Provider email near 90% is not a budget-control system. Pravah needs scheduled usage polling and internal warning thresholds comfortably below provider enforcement, plus orphan reconciliation, cleanup-retry visibility, and a safe response when uploads are refused.
- Fixed Free/Plus/Advanced plans do not document automatic monetary overage; persistent excess risks disablement after warnings. Pro PAYG can bill overage. Consequently, the chosen plan and billing mode must be explicit before enabling production uploads.

## Account facts still required

These cannot be established from public documentation or the repository and need the actual Cloudinary Console/account owner:

1. Product environment/cloud name, account plan and billing mode, and whether production uses a separate environment from development.
2. Current 30-day transformation, storage, and image-bandwidth usage, including any unrelated assets sharing the account.
3. API data-center region. AP provisioning is Enterprise-only and must be arranged at account creation, so a self-service plan implies the default US region.
4. Whether Strict Transformations and automatic backup are enabled.
5. Whether signed-URL invalidation is enabled; if not, whether Cloudinary Support will enable it on the selected plan.
6. Whether authenticated delivery and all intended eager variants work on that exact plan, and—if short-lived CDN access is required—whether an Advanced token encryption key has been provisioned.
7. Account-specific concurrency ceilings, any custom limits, alert recipients, and the operational owner responsible for usage warnings.

## Acceptance gates for later specification

- Record the selected privacy model and plan; do not describe permanent bearer URLs as session-private.
- Keep the API secret exclusively in authenticated server-side configuration; authorize and rate-limit every signature request.
- Use authenticated image assets with a bounded eager-variant allowlist unless the delivery decision chooses a different verified mechanism.
- Normalize the stored master and strip EXIF/IPTC/XMP before persistence; enforce server-side type, dimensions, and byte ceilings.
- Store Cloudinary's immutable asset ID plus provider-neutral Pravah metadata; do not make delivery URLs the record identity.
- Delay provider deletion until recovery expiry, purge any enabled backups, request cache invalidation, retry failures, and reconcile orphans.
- Poll usage and alert below Cloudinary's approximate 90% warning point; validate actual costs with a measured Android prototype before rollout.
