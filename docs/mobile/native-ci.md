# Native workflow and performance CI

`Mobile native CI` builds a fresh Android release APK on every PR and main push, then runs it on an API 35 Pixel 6 emulator. All compilation and validation run in GitHub Actions.

The first precheck exposed Expo 56's Hermes V1 memory regression. This PR upgrades to Expo 57 and React Native 0.86.3 with the corrected Hermes compiler, aligns native SDK dependencies, and ports the existing Android clipboard patch to expo-clipboard 57.0.2. This requires a new native binary. See [Expo's regression notes](https://expo.dev/changelog/sdk-57#known-regressions).

The SDK 57 release graph also exhausted Expo's default 512 MiB Gradle metaspace during native lint. The prebuild plugin keeps a 2 GiB heap and raises metaspace to 1 GiB, with immediate exit on memory exhaustion. CI serializes project execution, caps compilation at 30 minutes, captures delayed process/thread evidence, and saves a successful build cache before device tests. Native lint remains enabled.

The `com.pravah.mobile.e2e` variant runs the production App, screens, sheets, keyboard and native dependencies with a deterministic in-memory transport. Metro replaces only Convex/auth modules for this CI-only variant. It contains 500 tasks and one goal. A loopback provider fixture checks that Kairo's actual prompt contains scheduled tasks. Native Observe remains active with a nil project UUID and a loopback export sink, so it can initialize without sending CI measurements to the production project. No production backend, Google login, provider key, release upload or OTA is used. EAS rejects this variant and updates are disabled.

The native workflow covers launch, capture, keyboard-visible save, title edit, completion, Timeline, Goals detail, Progress history, settings, and Kairo. These checks exercise the native UI with fixture transport. Google sign-in, Convex connectivity/auth enforcement, real notification delivery, image-provider delivery and OTA installation still need separate integration/device verification.

The performance checks collect five cold launches to the app's interactive marker, raw native activity-launch output, a large-Inbox scroll, window frame timings and process memory. Startup budgets are a median interactive time at most 8 seconds and every startup at most 15 seconds. Scroll frame p95 may regress at most 20% from the checked-in baseline of 150.278484 ms, giving an initial 180.334181 ms limit. The 100 ms target remains visible in each result as `meetsTarget`, not an assertion that the baseline already meets it. Missing markers or insufficient frames fail the check. The host-observed startup value includes ADB polling overhead. The frame data is coarse Android `gfxinfo` evidence and does not replace Perfetto or physical-device tracing. Memory is recorded without a gate until a repeatable baseline exists.

The fixed API 35 Pixel 6 profile uses a 720 × 1600 display at 280 dpi, preserving its logical layout while reducing the software renderer's pixel cost. Display overrides are saved with the evidence. The first full 1080 × 2400 run passed both Maestro flows and startup (4,038 ms median), but failed the unchanged 100 ms frame budget at 219.83 ms p95. Its median `SwapBuffers` to `FrameCompleted` interval alone was 59.05 ms. This prompted the lower-resolution emulator configuration, not a claim of an app rendering improvement. [Android's emulator source documentation recommends reducing AVD resolution for SwiftShader performance](https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android/docs/GPU-EMULATION.TXT). Compare frame results only at the same display configuration.

The timed scroll runs after the Maestro functional assertions finish, using six upward and six downward ADB swipes of 600 ms each. It resets frame statistics immediately before those gestures. This avoids measuring Maestro hierarchy/screenshot inspection alongside scrolling. The protocol, raw frame data from the preceding Maestro flow, timed frame data and memory are retained. The earlier 720 × 1600 run measured 150.16 ms p95 during Maestro; results across these different measurement protocols are not an app speedup comparison.

`Mobile persistence performance` compares the old byte-limited diagnostics retention algorithm at `55b1275` with the new algorithm on the same fixture, checks identical retained results, and saves seven-sample median times. It measures host JavaScript pruning cost. It does not measure app startup, FPS, battery, or the overall app speedup.

Download `mobile-native-evidence` for the tested revision, emulator build fingerprint, Maestro JUnit reports, screenshots, logcat, startup samples, frame statistics and memory. Download `mobile-persistence-benchmark` for the algorithm comparison. No retry conceals a failing native flow.

The checks fail the workflow on regression. Making them mandatory for merges requires repository rules to require the exact check names `Android native workflows and performance` and `Mobile persistence performance`. At implementation time, the GitHub API reported that `main` was not protected; adding this workflow does not change repository branch rules.

References: [Expo native builds](https://docs.expo.dev/guides/local-app-overview/), [Maestro reports](https://docs.maestro.dev/maestro-flows/workspace-management/test-reports-and-artifacts), [Android frame/startup metric definitions](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics). The generated APK is intentionally a release build so production JavaScript behavior and native bundling are exercised without Metro running during tests.

The first controlled-scroll run at `2c2bb3d` measured 123.17 ms median and 150.28 ms p95 over 116 valid frames, exceeding the provisional 100 ms target. Removing Maestro inspection did not improve that result. `scripts/mobile-performance/native-baseline.json` records that source revision, run, display, API, protocol and measured p95. The regression limit is a policy allowance of 20%, not an app speedup or a production frame-time goal. Baselines must be reviewed explicitly rather than automatically replaced by each run. Real-device rendering attribution remains open.
